# Lance 性能指南

本指南提供了优化 Lance 应用性能的技巧和窍门。

## 日志

Lance 使用 `log` crate 来记录消息。显示这些日志消息取决于你使用的客户端库。对于 Rust，你需要配置日志订阅器。更多详情请参阅 [log](https://docs.rs/log/latest/log/) 文档。Python 和 Java 客户端配置了默认的日志订阅器，输出到 stderr。

Python/Java 日志记录器可以通过以下环境变量配置：

- `LANCE_LOG`：基于日志级别和目标控制日志过滤。更多详情请参阅 [env_logger](https://docs.rs/env_logger/latest/env_logger/) 文档。`LANCE_LOG` 环境变量取代了 `RUST_LOG` 环境变量。
- `LANCE_TRACING`：基于日志级别控制追踪过滤。下面描述的关键追踪事件在 `info` 级别发出。但在 `debug` 级别有额外的 span 和事件可用，可能对调试性能问题有用。默认追踪级别为 `info`。
- `LANCE_LOG_STYLE`：控制日志消息中是否使用颜色。有效值为 `auto`、`always`、`never`。
- `LANCE_LOG_TS_PRECISION`：日志消息中时间戳的精度。有效值为 `ns`、`us`、`ms`、`s`。
- `LANCE_LOG_FILE`：将 Rust 日志消息重定向到指定的文件路径而非 stderr。设置后，Lance 将创建文件和任何必要的父目录。如果无法创建文件（例如权限问题），Lance 将回退到 stderr 输出。

## 追踪事件

Lance 使用 tracing 来记录事件。如果你正在运行 `pylance`，这些事件将作为日志消息发出。对于 Rust 连接，你可以使用 `tracing` crate 来捕获这些事件。

### 文件审计

文件审计事件在创建或删除重要文件时发出。

| 事件                | 参数      | 描述                                                              |
| ------------------- | --------- | ---------------------------------------------------------------- |
| `lance::file_audit` | `mode`    | I/O 操作模式（create、delete、delete_unverified）                  |
| `lance::file_audit` | `type`    | 受影响的文件类型（manifest、data file、index file、deletion file）   |

### I/O 事件

I/O 事件在执行重要的 I/O 操作时发出，特别是与索引相关的操作。当索引从内存缓存加载时，这些事件**不会**发出。正确的缓存利用对性能很重要，这些事件旨在帮助你调试缓存使用情况。

| 事件               | 参数      | 描述                                                                                       |
| ------------------ | --------- | ----------------------------------------------------------------------------------------- |
| `lance::io_events` | `type`    | I/O 操作类型（open_scalar_index、open_vector_index、load_vector_part、load_scalar_part）    |

### 执行事件

执行事件在运行执行计划时发出。这些事件对调试查询性能很有用。

| 事件               | 参数                | 描述                                                   |
| ------------------ | ------------------- | ----------------------------------------------------- |
| `lance::execution` | `type`              | 执行事件类型（目前仅有 plan_run）                        |
| `lance::execution` | `output_rows`       | 计划输出中的行数                                        |
| `lance::execution` | `iops`              | 计划执行的 I/O 操作数                                   |
| `lance::execution` | `bytes_read`        | 计划读取的字节数                                        |
| `lance::execution` | `indices_loaded`    | 计划加载的索引数                                        |
| `lance::execution` | `parts_loaded`      | 计划加载的索引分区数                                     |
| `lance::execution` | `index_comparisons` | 各种索引内部执行的比较次数                                |

## 线程模型

Lance 被设计为线程安全且高性能的。除非另有说明，Lance API 可以并发调用。用户可以创建多个表并在线程间共享表。操作可以在同一张表上并行运行，但某些操作可能导致冲突。详情请参阅[冲突解决](../format/table/transaction.md#conflict-resolution)。

大多数 Lance 操作会使用多个线程并行执行工作。Lance 中有两个线程池：IO 线程池和计算线程池。IO 线程池用于从磁盘读写数据。计算线程池用于对数据执行计算。每个线程池中的线程数可由用户配置。

IO 线程池用于从磁盘读写数据。IO 线程池中的线程数由操作所使用的对象存储决定。本地对象存储默认使用 8 个线程。云对象存储默认使用 64 个线程。这是相当保守的默认值，你可能需要 128 或 256 个线程才能在某些云提供商上饱和网络带宽。可以使用 `LANCE_IO_THREADS` 环境变量覆盖 IO 线程数。如果增加此变量，你可能还需要增加 `io_buffer_size`。

计算线程池用于对数据执行计算。计算线程池中的线程数由机器的核心数决定。可以通过设置 `LANCE_CPU_THREADS` 环境变量覆盖计算线程池中的线程数。当在同一台机器上运行多个 Lance 进程时（例如使用 Ray 等工具时），通常需要这样做。请记住，解码数据是计算密集型操作，即使工作负载看起来是 I/O 密集型的（如扫描表），它仍可能需要相当多的计算线程才能达到峰值性能。

## 内存需求

Lance 被设计为内存高效的。操作应从磁盘流式传输数据，而不需要将整个数据集加载到内存中。但是，Lance 的一些组件可能会使用大量内存。

### 元数据缓存

Lance 使用元数据缓存来加速操作。此缓存保存各种元数据片段，如文件元数据、数据集清单等。此缓存是一个按字节大小限制的 LRU 缓存。默认大小为 1 GiB。

默认情况下，元数据缓存不在表之间共享。为了获得最佳性能，你应该创建单个表并在应用程序中共享它。或者，你可以创建单个会话并在打开表时指定它。

键通常是多个字段的组合，所有键都以数据集 URI 为作用域。以下项目存储在元数据缓存中：

| 项目              | 键                                               | 存储内容                        |
| ----------------- | ------------------------------------------------ | ------------------------------- |
| 数据集清单         | 数据集 URI、版本和 etag                            | 数据集的清单                     |
| 事务              | 数据集 URI、版本                                   | 数据集的事务                     |
| 删除文件           | 数据集 URI、fragment_id、版本、id、file_type        | 片段的删除向量                   |
| 行 ID 掩码         | 数据集 URI、版本                                   | 数据集的行 ID 序列               |
| 行 ID 索引         | 数据集 URI、版本                                   | 数据集的行 ID 索引               |
| 行 ID 序列         | 数据集 URI、fragment_id                            | 片段的行 ID 序列                 |
| 索引元数据         | 数据集 URI、版本                                   | 数据集的索引元数据               |
| 索引详情¹          | 数据集 URI、索引 uuid                              | 索引的索引详情                   |
| 文件全局元数据      | 数据集 URI、文件路径                               | 文件的全局元数据                  |
| 文件列元数据       | 数据集 URI、文件路径、列索引                        | 列的搜索缓存                     |

注意：

1. 仅对非常旧的索引存储，这些索引不在清单中存储其详情。

### 索引缓存

Lance 使用索引缓存来加速查询。它在内存中缓存向量和标量索引。此缓存的最大大小可以在创建 `LanceDataset` 时使用 `index_cache_size_bytes` 参数配置。此缓存是一个按字节大小限制的 LRU 缓存。默认大小为 6 GiB。你可以通过检查 `dataset.session().size_bytes()` 的结果来查看此缓存的大小。

索引缓存不在表之间共享。为了获得最佳性能，你应该创建单个表并在应用程序中共享它。

**注意**：`index_cache_size`（按条目数指定）自版本 0.30.0 起已弃用。新代码请使用 `index_cache_size_bytes`（按字节指定）。

### 扫描数据

搜索（例如向量搜索、全文搜索）不会使用大量内存来保存数据，因为它们通常不返回大量数据。但是，扫描数据可能使用大量内存。扫描是流式操作，但我们需要足够的内存来保存正在扫描的数据。所需的内存量主要由 `io_buffer_size` 和 `batch_size` 变量决定。

每个 I/O 线程应有足够的内存来缓冲整个页面的数据。目前页面大小通常在 8 到 32 MB 之间。这意味着，作为经验法则，你通常应该为每个 I/O 线程准备约 32MB 的内存。默认的 `io_buffer_size` 为 2GB，足以缓冲 64 个数据页。如果你增加 I/O 线程数，也应增加 `io_buffer_size`。

扫描还将在 CPU 线程上并行解码数据（并运行任何过滤或计算）。任何时刻解码的数据量由 `batch_size` 和行的大小决定。每个 CPU 线程需要足够的内存来容纳一个批次。一旦批次交付给你的应用程序，Lance 就不再追踪它们，因此如果内存是个问题，你也应注意不要在自己的应用程序中累积内存（例如通过运行 `to_table` 或以其他方式在内存中收集所有批次）。

默认的 `batch_size` 为 8192 行。当你主要处理标量数据时，你希望批次大约为 1MB，因此计算线程所需的内存量相当小。但是，当处理大型数据时，你可能需要调低 `batch_size` 以控制内存使用。例如，处理 1024 维向量嵌入（例如 32 位浮点数）时，8192 行将是 32MB 数据。如果分布在 16 个 CPU 线程上，每次扫描需要 512MB 的计算内存。你可能会发现每批次 1024 行更合适。

总之，扫描最多可能使用 `(2 * io_buffer_size) + (batch_size * num_compute_threads)` 字节的内存。请记住，`io_buffer_size` 是软限制（例如，目前我们无法一次读取少于一个页面），因此如果你看到内存使用略微超过此限制，这不一定是错误。

### 云存储限流

云对象存储（S3、GCS、Azure）会自动使用 AIMD（加法增加/乘法减少）速率限制器进行封装。当存储返回限流错误（HTTP 429/503）时，请求速率会乘法减少。在持续成功期间，速率会加法增加。这适用于所有操作（读取、写入、删除、列表），并取代了旧的 `LANCE_PROCESS_IO_THREADS_LIMIT` 进程级限制。

本地存储和内存存储**不会**被限流。

AIMD 限流器可以通过存储选项或环境变量进行调整。存储选项优先于环境变量：

| 设置               | 存储选项键                          | 环境变量                          | 默认值 |
| ------------------ | --------------------------------- | --------------------------------- | ------ |
| 初始速率           | `lance_aimd_initial_rate`         | `LANCE_AIMD_INITIAL_RATE`         | 2000   |
| 最小速率           | `lance_aimd_min_rate`             | `LANCE_AIMD_MIN_RATE`             | 1      |
| 最大速率           | `lance_aimd_max_rate`             | `LANCE_AIMD_MAX_RATE`             | 5000   |
| 减少因子           | `lance_aimd_decrease_factor`      | `LANCE_AIMD_DECREASE_FACTOR`      | 0.5    |
| 加法增量           | `lance_aimd_additive_increment`   | `LANCE_AIMD_ADDITIVE_INCREMENT`   | 300    |
| 突发容量           | `lance_aimd_burst_capacity`       | `LANCE_AIMD_BURST_CAPACITY`       | 100    |

这些初始设置是平衡的，应适用于大多数场景。例如，S3 通常可以达到 5000 req/s，使用这些设置我们应该能在约 10 秒内达到该速率。

## 冲突处理

Lance 使用乐观并发控制（Optimistic Concurrency Control）支持对同一张表的并发操作。当两个操作冲突时，其中一个必须重试。重试会自动处理，但它们会重复已完成的工作，这可能影响吞吐量。理解和减少冲突对于在写入密集型工作负载中保持良好性能很重要。

常见的冲突来源包括：

- 并发压缩和索引构建，因为两者都需要修改相同的索引
- 影响相同片段的更新操作，因为两者都需要重写相同的数据文件

关于哪些操作之间会冲突的更多详情，请参阅[冲突解决](../format/table/transaction.md#conflict-resolution)。

### 片段复用索引（Fragment Reuse Index）

压缩是最昂贵的写入操作之一，因为它重写数据文件，且默认情况下会重映射所有索引以反映新的行地址。当压缩和索引构建并发运行时，它们经常冲突，因为两者都需要修改相同的索引。这通常导致压缩失败并重试，反复失败可能导致表布局随时间退化。

片段复用索引（FRI）通过允许压缩跳过索引重映射步骤来解决此问题。压缩不再立即更新索引，而是记录从旧片段行地址到新地址的映射。当索引加载到缓存中时，FRI 被应用以将旧行地址转换为当前地址。这会给索引加载时间增加少量开销，但一旦索引被缓存就不影响查询性能。

这种解耦意味着压缩和索引构建不再冲突，这对于持续摄入数据同时维护索引的表特别有价值。

要启用 FRI，在压缩时设置 `defer_index_remap=True`：

```python
dataset.optimize.compact_files(defer_index_remap=True)
```

有关索引格式和使用模式的详情，请参阅[片段复用索引规范](../format/table/index/system/frag_reuse.md)。

## 索引

训练和搜索索引可能对计算和内存有独特要求。本节提供了不同索引类型的预期指导。

### BTree 索引

BTree 索引是一个两级结构，提供高效的范围查询和有序访问。它在包含所有值的昂贵内存结构和无法高效搜索的昂贵磁盘结构之间取得平衡。

训练 BTree 索引通过排序列来完成。这使用[外部排序](https://en.wikipedia.org/wiki/External_sorting)来将总内存使用控制在合理范围内。更新 BTree 索引不需要重新排序整个列。新值会被排序，然后在线性时间内合并到现有排序值中。

#### 存储需求

BTree 索引本质上是列的排序副本。因此存储需求与列相同，但每个值需要额外 4 字节来存储行 ID，还有一个小的查找结构，大约为列大小的 0.001%。

#### 内存需求

训练 BTree 索引需要一些 RAM，但当前实现会积极地溢出到磁盘，因此总内存使用相当低。

搜索 BTree 索引时，索引按页加载到索引缓存中。每页包含 4096 个值。

#### 性能

排序阶段是训练 BTree 索引中最昂贵的步骤。时间复杂度为 O(n log n)，其中 n 是列中的行数。在非常大的规模下，这可能成为瓶颈，可能需要分布式排序。Lance 目前没有内置此功能，但正在开发中。如果你有灵活性，随着数据增长分段训练索引可能比一次训练整个索引稍微更高效。

当 BTree 索引完全加载到索引缓存中时，搜索时间与匹配查询的行数线性增长。当 BTree 索引未完全加载到索引缓存中时，搜索时间将由需要从磁盘加载的页数和存储速度控制。执行指标中的 parts_loaded 指标可以告诉你为满足查询从磁盘加载了多少页。

### Bitmap 索引

Bitmap 索引是一个倒排查找表，为列中每个可能的值存储一个位图。这些位图被压缩并序列化为 [Roaring Bitmap](https://roaringbitmap.org/)。

Bitmap 索引目前通过将列累积到从值到行 ID 向量的哈希映射中来训练。然后每个值被序列化为位图并存储在文件中。

### 存储需求

Bitmap 索引的大小难以精确计算，但通常与列中唯一值的数量成正比，因为每个值需要一个唯一位图，且包含所有行的单个位图比许多只有少量行的位图压缩更高效。

#### 内存需求

由于训练 Bitmap 索引需要将值收集到哈希映射中，你至少需要每行 8 字节的内存。此外，如果你有很多唯一值，则需要额外的内存用于哈希映射的键。大规模训练具有许多唯一值的大型位图可能会占用大量内存。

搜索 Bitmap 索引时，位图会单独加载到会话缓存中。位图的大小取决于匹配该标记的行数。

### 性能

当 Bitmap 索引完全加载到索引缓存中时，搜索时间与查询所需的值数量线性增长。这使得 Bitmap 对于等值查询或非常小的范围非常快。对大范围的查询目前非常慢，BTree 索引对大范围查询快得多。

当 Bitmap 索引未完全加载到索引缓存中时，搜索时间将由需要从磁盘加载的位图数量和存储速度控制。执行指标中的 parts_loaded 指标可以告诉你为满足查询从磁盘加载了多少位图。

### 向量索引

向量索引（IVF_PQ、IVF_HNSW_SQ 等）分多个阶段构建，每个阶段有不同的内存需求。

#### IVF 训练

IVF（倒排文件）阶段使用 KMeans 将向量聚类到分区中。为了训练 KMeans 模型，数据集的一个样本被加载到内存中。样本大小由以下公式决定：

```
training_data = num_partitions * sample_rate * dimension * sizeof(data_type)
```

默认的 `sample_rate` 为 256。例如，使用 1024 个分区、768 维 float32 向量和默认采样率：

```
1024 * 256 * 768 * 4 bytes = 768 MiB
```

除了训练数据外，每次 KMeans 迭代还会分配与训练向量数量成比例的成员和距离向量（每个向量 8 字节）。质心本身需要 `num_partitions * dimension * sizeof(data_type)` 字节。实际上，训练数据占主导地位，这些额外分配相比之下很小。

如果数据集的行数少于 `num_partitions * sample_rate`，则使用整个数据集进行训练。

#### 量化器训练

IVF 训练后，训练量化器（例如 PQ、SQ）来压缩向量。此阶段可能对数据集进行一些采样，但样本大小与量化器的属性和向量维度相关，而非数据集的大小。因此，量化器训练通常比 IVF 阶段需要的 RAM 少得多。

#### 洗牌（Shuffling）

最后阶段扫描整个向量列，转换每个向量（将其分配到 IVF 分区并量化），然后将结果写入磁盘上的每分区文件。这是一个流式操作 — 数据不会在内存中累积。

输入扫描默认使用 2 GiB I/O 预读缓冲区（可通过 `LANCE_DEFAULT_IO_BUFFER_SIZE` 配置），以 8,192 行为批次读取。传入的批次并行转换，同时有 `num_cpus - 2` 个批次在处理中（可通过 `LANCE_CPU_THREADS` 配置）。每个批次按分区 ID 排序，切片直接写入相应的分区文件。此阶段的运行中内存大约为：

```
io_readahead_buffer + num_cpu_threads * batch_size * (raw_vector_size + transformed_vector_size)
```

每个分区有一个打开的文件写入器，大约有 8 MiB 的累积缓冲区。实际上，单个分区中不应有那么多数据累积。相反，最大累积将大约是分区的最终大小，即 `num_rows * (num_sub_vectors + 8) bytes`。例如，1 亿行 1536 维向量将有 96 个子向量，因此最大累积约为 ~10GB。每行额外的 8 字节用于行 ID。

#### 存储需求

向量索引的磁盘大小由 IVF 质心和量化向量组成。

质心需要：

```
num_partitions * dimension * sizeof(data_type)
```

这通常很小。例如，10K 个分区和 768 维 float32 向量仅为 30 MiB。

量化向量构成索引的大部分。每行存储一个量化码加上 8 字节行 ID。确切大小取决于量化器：

**PQ（乘积量化）：** 每个子向量被量化为单个字节，因此每行需要 `num_sub_vectors + 8` 字节。例如，1 亿行 96 个子向量：

```
100M * (96 + 8) = ~9.7 GiB
```

**SQ（标量量化）：** 每个维度独立量化为单个字节，因此每行需要 `dimension + 8` 字节。SQ 比 PQ 保留更多信息但需要更多存储。例如，1 亿行 768 维向量：

```
100M * (768 + 8) = ~72.3 GiB
```

**RQ（RaBitQ）：** 向量被量化为二进制码，每个维度可配置位数。每行还存储用于距离校正的每行缩放和偏移因子（各 4 字节）。每行需要 `dimension * num_bits / 8 + 16` 字节（8 字节用于行 ID 加上 8 字节用于因子）。例如，1 亿行 768 维 1 bit/维度：

```
100M * (768 * 1 / 8 + 16) = ~10.8 GiB
```
