# 发布指南

Lance 项目的发布应尽可能通过 GitHub Actions 自动化。
此类自动化包括版本号递增、标记破坏性变更、发布制品和生成发布说明。
总体而言，我们的目标是将人工交互最小化，仅需通过 GitHub Actions 发起发布
并在 GitHub Discussions 上对发布进行投票。

## 发布类型

Lance 项目遵循两种发布类型：

- **预览版**（也称为 Beta 版）：维护者可以随时发布预览版以使用最新变更。
  预览版不提供稳定性保证，仅用于早期测试和反馈。

- **稳定版**：拥有写入权限的维护者可以随时在 GitHub Discussions 中发起稳定版发布。
  稳定版必须经过投票流程。
  稳定版发布发起后，鼓励社区验证发布中是否存在潜在 Bug 并进行投票。
  PMC 负责正式投出稳定版发布的约束性投票。投票通过后，
  维护者可以继续完成稳定版发布。

## 发布版本号

所有 Lance 项目遵循 [语义化版本](https://semver.org/) 规范进行版本管理：

- **主版本号**（`X.0.0`）：不向后兼容的破坏性变更时递增
- **次版本号**（`0.X.0`）：向后兼容的新功能时递增
- **补丁版本号**（`0.0.X`）：关键修复时递增

预览版使用 `-beta.X` 预发布后缀附加到目标稳定版本号上（例如 `1.2.3-beta.1`、`1.2.3-beta.2`）。

请注意，与从 main 分支切出的主版本和次版本发布不同，
补丁版本发布应基于现有的主版本、次版本或补丁版本的提交进行。
补丁版本应仅包含针对安全漏洞、重大正确性问题、
重大性能退化或回滚意外破坏性变更等关键情况的修复。
任何补丁版本中的修复都应在 main 分支中有对应的修复。
强烈不建议为旧版本持续添加补丁版本。

对于主版本发布，建议包含一份迁移指南，帮助用户了解如何
处理主版本中引入的任何破坏性变更。

## 项目特定发布流程

每个项目在名为 `release_process.md` 的文件中维护其详细的发布流程。
项目特定发布流程的变更被视为普通代码修改，可由拥有写入权限的维护者批准。
